# Duplicate recall slots, measured before and after the collapse

Produced 2026-08-23T13:32:24Z by `scripts/recall_dup_slot_measure.py` at commit `3b335021b8de`. Every number below is regenerated by that script from the committed selection; the one hand-written section says so.

## The headline

Over **2000 replayed real recall requests** (13254 delivered slots), the share of slots occupied by a repeat of a higher-ranked slot of the same answer falls from **2.39%** to **0.95%** — 317 occupied slots down to 126, a 60.3% reduction. 216 slots changed delivery class.

Answers carrying at least one repeat in a slot: 220 of 2000 (11.0%) before, 109 (5.5%) after.

That gain is not free, and the cost is not clean: of 256 collapsed slots, 60 came from pairs where the collapsed node named 3 or more identifiers (timestamps, PIDs, commit hashes, ticket ids) that its bearer never mentions. Read *What the collapse cost* and the hand-written spot check below before quoting the headline.

The flag is the only difference, and that is checked rather than assumed: across all 2500 replayed answers the two arms returned the identical ranked node ids (0 mismatching answers). Only the delivery class differs.

### The definition of a repeat, used identically for both arms

> A delivered slot whose node is byte-identical to, or has mean-pooled chunk-vector cosine strictly above 0.95 with, a HIGHER-RANKED slot of the same answer. Computed by this script from the ranked answer, identically for both arms.
>
> A repeat slot the arm shipped with content (delivery in ['full', 'snippet']) instead of a content_ref stub.
>
> duplicate-slot share = occupied repeat slots / delivered slots

### The query set

Events with a non-empty query, ordered by recall_events.id (ULID, so chronological). Stratum 'events': random.Random(seed).sample over that ordering, i.e. traffic-weighted -- a query asked 40 times can be drawn 40 times, which is what makes the slot counts represent slots actually delivered in the field. Stratum 'distinct_queries': the distinct query texts, each represented by its earliest event, sampled the same way with seed+1 -- one vote per query text, so a handful of hot queries cannot carry the result. Both strata are replayed with each event's own recorded requested_scope, depth and max_results.

## What the collapse cost

- **256 slots collapsed**, replacing 571,519 characters of delivered text with a `content_ref` stub.
- **Length-guard near-misses: 80** (31.2% of collapsed slots) — collapsed slots whose own content was LONGER than the bearer's but not by more than the guard's ratio, so the extra text became a stub. Total text collapsed away in excess of the bearer: 20,085 characters; worst length ratio 1.1855 against a guard that fires above 1.20.
- **Length-guard vetoes: 185** — repeat slots left content-bearing because the candidate exceeded its bearer by more than the guard's ratio -- the 'same fact plus a new detail' case the guard exists for. These slots stayed full-text on purpose.
- **Repeats no vector could see: 0** — repeat slots that stayed content-bearing because a node had no usable chunk vectors (never drained, or mixed widths).

## Spot check: was any collapsed pair two different facts?

80 distinct collapsed pairs, each re-checked with arithmetic that shares nothing with the embedding model. Independent of the embedding model: Unicode word tokens, set Jaccard, 5-gram shingle containment, and difflib ratio over the first 4000 characters. The difflib ratio is the weakest of the three on long nodes -- it is order-sensitive and sees only that prefix, so a reordered digest scores low while Jaccard and containment still show the two texts are the same material.

Token Jaccard across those pairs: median 0.7333, p25 0.5673, min 0.2065. 5-gram containment of the collapsed node in its bearer: median 0.7561, min 0.0215.

A second, sharper mechanical check runs over all 80 pairs: **identifier loss** — Identifier-shaped tokens (>=5 chars, carrying a digit: timestamps, PIDs, commit hashes, ticket ids, goal-node names) present in the collapsed node and absent from its bearer. The full node stays reachable through memory_lookup; this counts what the answer itself stopped showing.

- **34 of 80 pairs lose no identifier at all**: the bearer already carries everything the collapsed node named.
- **14 pairs lose 3 or more identifiers**, accounting for **60 of 256 collapsed slots**. These are the collapses where the answer stopped showing specifics — read them below before trusting the headline.

- **8 collapsed slots point at a bearer they never matched** (4 of 80 pairs, lowest cosine 0.904395): collapsed pairs whose cosine to the RECORDED bearer is at or below the collapse threshold, because bearer resolution walks to the root of the duplicate chain. The collapse is still earned — the node did exceed the threshold against some higher-ranked slot — but the `content_ref` an agent is handed names a weaker match than the one that earned the stub.

## Manual reading of the flagged pairs

*Hand-written. This is the one section `recall_dup_slot_measure.py` does not
generate: re-running it rewrites every other section and drops this one, which
has to be re-appended. Everything it asserts is checkable against the table
above and the node ids in the JSON.*

(On the snapshot line above: the live file was opened read-only and copied out
with `VACUUM INTO` at the start of this session's first run, and every run since
— including this one — was pointed at that one 627 MiB snapshot, byte-identical
and sha256-pinned. That is deliberate: repeated runs are only comparable if the
corpus underneath them does not move, and the live database gains events every
minute. The live file has never been opened for writing by anything here.)

I opened both texts of all 26 pairs listed above — every pair that tripped
either mechanical check — on the read-only truth copy. The other 54 pairs (162
of the 256 collapsed slots) I did not read individually: they clear token
Jaccard 0.6 *and* lose fewer than three identifiers, which is the case both
checks were built to clear.

**The answer to the section's question is no — not every collapsed pair was one
fact.** By slot, over the 94 slots those 26 pairs produced:

| verdict | pairs | slots | what it means |
| --- | ---: | ---: | --- |
| one fact, bearer carries it | 9 | 18 | correct collapse; several are a schema digest quoting its own source trace verbatim (containment 1.00) |
| one rule, **different incident** | 7 | 31 | the lesson is the same, the ticket/run/timestamp it was learned on is not |
| **two different facts** | 9 | 33 | the bearer never states what the collapsed node states |
| one fact, **detail lost** | 1 | 12 | the length-guard near-miss: the collapsed node was the longer superset |

**Where the wrong collapses live.** Eight of the nine "two different facts"
pairs are `schema`/`schema`. Schema nodes here are consolidation's procedural
digests: each opens with `Procedure: <name>` and continues in a rigid skeleton,
so mean-pooling over their chunks yields a vector dominated by the template.
Two digests describing genuinely different incidents then clear 0.95:

- `01KT7C5RKH6QAV6Z8SB19G5QDP` — an Octopus supervision snapshot taken ~16:10,
  naming PIDs 1779345/1784372 — collapsed into `01KT4WNA0M9Q2Z7111XWQ8EFV9`, a
  *14:42* scan of the same project with different findings, at cosine 0.9524,
  in **10 delivered slots**. Different scans, different state, different facts.
- `01KVFRV26V42KX58EF6B9PCNFJ` ("p15c a03 datasets") collapsed into
  `01KV68151P7F05H6NVR85BPQEH` ("p7b v2 fresh evidence") at 0.9524, losing 19
  identifiers. Two unrelated pieces of work that share a report template.
- Four `Procedure: reopen lesson` digests for four different tickets
  (EZ-12826, EZ-13392, EZ-13512, ADS-1387) collapsed into each other or into
  one bearer at 0.90–0.96. The generalisable rule they teach *is* the same; the
  ticket, the MR and the evidence path are not — those are the 31 "different
  incident" slots.

`trace`/`trace`, the level that carries most traffic, behaves as intended: 46
pairs, 149 slots, 3 identifier-losers, median Jaccard 0.82. And every
`trace`/`schema` pair (13 pairs, 18 slots) is the concept-over-its-own-sources
band the root goal describes — the digest contains the trace verbatim, so
stubbing the trace under it on delivery is exactly right.

**Both mechanical checks are imperfect, in both directions.** Identifier loss
over-counts on formatting variants: `01KS998AZ5N441AMX8M273J8X1` and
`01KS96N74Z9GN1F652A7HSC047` are two write-ups of the *same* verification of
the same node on the same day, and the five "lost" identifiers are `f106824a`
against `f106824a1550` and similar. It under-counts when the distinguishing
name carries no digit: the two `Procedure: stagnation detection` digests
(pair 1) differ in the goal *paths* they list and register only two lost
identifiers. That is why 14 pairs trip the check and 9 pairs fail my reading —
the two sets overlap but neither contains the other.

**What I did not do: tune the threshold.** No arm was run at any other cosine.
The sensitivity table below moves the *definition* of a repeat, not the
collapse threshold, and says nothing about what a 0.97 collapse would deliver —
that is an experiment this node did not run. What the data does say is that
**level discriminates better than cosine here**: the wrong collapses sit
between 0.93 and 0.98, overlapping the correct ones completely, while 8 of 9 of
them are `schema`/`schema`, a level that is 18 of 80 pairs. A follow-up that
wants a cleaner collapse should look at excluding template-shaped schema
digests, not at moving the number.

**What none of this undoes.** A stub is not a deletion: `content_ref` keeps the
full node one `memory_lookup` away, the byte-exact twin dedup is untouched, and
`LM_RECALL_NEAR_DUP_COSINE=0` restores the old behaviour without a revert. The
measured gain — 2.39% → 0.95% of slots occupied by a repeat, holding at
3.26% → 1.55% on the one-vote-per-query stratum — stands. It is bought at the
cost of 33 slots in 2,000 answers where an agent had to follow a `content_ref`
to find a fact the answer stopped stating.

**Superseded in one respect, by the finding above it.** The `bearer_chaining`
row of this run — 4 pairs, 8 slots, cosine to the recorded bearer as low as
0.904 — was a defect, not a cost: `build_duplicate_map` chained a match through
a node that had itself become a stub, so the `content_ref` an agent was handed
named text the collapsed node had never been measured against, inside the
0.85–0.95 band where the root goal says different facts live. Cosine is not
transitive. That is now refused rather than recorded, and the frozen selection
was replayed again to measure the change:
`dup-slot-measurement-honest-bearer.json`, summarised in
`honest-bearer-remeasure.md`. Every number *above* this paragraph describes the
run at commit `3b335021b8de`, before that fix.
