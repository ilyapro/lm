Run it only after this root's product checks and ordinary gate pass and its accepted candidate is published on `refs/heads/master`. The exact accepted/published commit and publication receipt must come from the root's native `landing_publication` record, which binds the acceptance receipt, gate run, previous tip and actual ref update (`/home/sfx/p/ae/docs/publication-completion-contract.md`, “Receipt proof boundary”). A worktree commit, clean checkout or `PASS` text alone is insufficient.

1. Use the existing local deployment path in `docs/deployment.md`: confirm the published commit is the clean shared `/home/sfx/p/lm` `master` tip and the editable `living-memory` installation points there. Capture `/health` before the update, then use the normal local service update/restart. Do not deploy this worktree or touch the live database. 2. After restart, read one `/health` response. Require `ok`, a new `boot_id`, and `code_identity.status=known` with `scheme=python-loaded-functions-sha256-v2`. Compare `scheme` and `digest` with a prior response **of the same scheme**. An unknown identity or cross-scheme comparison is inconclusive. The digest represents covered in-memory Python function code, not the Git commit or every module global (`docs/deployment.md`, “Verify the running process”).
3. Use `scripts/check_deployed_protocol.py --json` from the published shared checkout to compare served MCP instructions and four public tool descriptions; exit 0 confirms only that protocol surface. For the code identity/source link, reuse the native observer primitives in `scripts/observe_live_task_recall.py`: authenticated `/admin/info` must agree with `/health`; `_candidate` independently imports the exact published commit; `_native_before` compares its v2 function digest to the service and verifies the installed editable import and published source bytes predate the process; `_native_projection` checks the same process and sources after the MCP call. Supply the *new goal's* relevant loaded path set and current prior v2 identity if a native completion command is bound. Its task-specific old cases and frozen command are not evidence for this goal.
4. Perform one authorized, read-only MCP `memory_recall` through the existing service/client path (`scope="project:lm"`, fixed `max_results`) on a safe current query selected for this change. Inspect the actual returned facts and distinctions and, if the case requires it, `memory_lookup` by an original id. Keep query, full response, private ids and detailed event body host-local; publish only a sanitized result count, repeat-slot count, whether the independent fact and distinctions appeared, lookup calls/bytes, response digest, event association, and execution time. If the live corpus offers no safe case with a recognized repeat and a displaced independent fact, report the transition as a smoke check, not a reproduced cost win. The committed synthetic paired run is the bounded efficacy proof; the live call checks uptake through the real MCP consumer.
5. Attach the root's actual publication receipt, loaded-code/installed-source observation, and sanitized MCP transition receipt to P4's existing verification. A changed boot plus matching protocol text alone does not attest changed retrieval behavior. Do not claim delivery if the observer fails or the read is inconclusive.
